# Better Batch — Cook View

**Date:** 2026-05-05
**Status:** Draft, pending implementation plan
**Amends:** `2026-05-04-better-batch-design.md` (adds a new top-level surface)

## 1. Overview

A real-time cooking view stripped of the editing/comparing/merging chrome. The user opens it when they're about to cook a batch (or re-cook a previously-cooked one) and uses it as their kitchen-side companion: it shows ingredients and steps, parses inline durations into clickable timers running in a sticky bottom dock, tracks elapsed cook time, lets the user check off steps as they go, captures quick notes for the next batch, and prompts to mark cooked at the end.

Mobile-first by design. Desktop layout reuses the same stacked structure (ingredients on top, steps below).

## 2. Route + entry point

**Route:** `src/routes/recipes/[id]/batches/[batchId]/cook/`. Loader returns 404 for missing recipe or batch. **No status redirect** — both `draft` and `cooked` batches can be cooked. (`archived` batches redirect to the recipe detail page.)

**Entry point:** A new `Cook` button on `BatchDetail`'s action bar.

- **Draft:** `+ New Batch` · **`Cook`** (Juniper filled, primary) · `…` menu.
  `Mark as Cooked` moves from its current spot into the `…` menu (still accessible for "I cooked elsewhere; just log it after the fact").
- **Cooked:** `+ New Batch` · **`Cook`** (label still "Cook"; functions as re-cook) · `Edit Outcome` · `…` menu.
- **Archived:** no `Cook` button.

The Cook button always navigates to the new route. Cook view itself reads `batch.status` to decide its tone.

## 3. Mode-aware behavior

Cook view runs in one of two modes, derived from `batch.status`:

- **first-cook (status === 'draft'):** the cook session ends by transitioning the batch to `cooked` (sets `cookedAt` to now, writes `outcomeNotes`, `rating`, and `cookDurationMs`).
- **re-cook (status === 'cooked'):** all batch data (ingredients, steps, variables, label, parentIds) stays frozen — the API already enforces this on PATCH for cooked batches. End-cook appends a timestamped note to existing `outcomeNotes`:

  ```
  {existing outcomeNotes}

  — 2026-05-15:
  {notes for this cook}
  ```

  `cookedAt` (the original first-cook date) is preserved. `cookDurationMs` is preserved (we don't track multiple session durations in MVP). Rating is preserved (no UI to change it from cook view; user uses `Edit Outcome` for that).

Checkboxes, timers, quick-notes, and elapsed-time tracking work identically in both modes.

## 4. Page layout (mobile-first stacked)

Single column. Components stack vertically, scroll within the steps list.

### 4.1 Top bar (sticky, full width)
- Left: back link `← {recipe.name}`
- Center: batch label · mode tag (`Cooking` for draft, `Re-cook` for cooked)
- Right: elapsed chip (rendered once `started === true`, e.g. `12 min`, `1h 12m`) · `End Cook` button (Juniper).

### 4.2 Start banner (pre-start, between top bar and ingredients)
Shown when `!started`:
- Body: "Press **Start Cooking** when you begin. Timers and notes can run anyway, but elapsed time only tracks once you start."
- Single button: `Start Cooking` (Juniper filled, primary).
- Click sets `started = true; startedAt = Date.now()`. Banner unmounts; elapsed chip appears in the top bar.

### 4.3 Ingredients section
- Header `Ingredients` (small uppercase tracker label).
- Below: a flex-wrap row of pills, each `{amount}{unit} {name}`. If a section is set on the ingredient, group pills by section with an inline `{section}:` label preceding the group. Section order = first-occurrence in the ingredient list (same as `IngredientList`).
- Pills used by the **current** step (defined as: the first unchecked step, or step 0 if none checked) get an Ochre tint background.
- Pills used **only** by checked steps get a subtle fade (`opacity-60`).
- Pills used by no step get default styling.

### 4.4 Steps section
- Header `Steps`.
- For each step (index `i`):
  - Layout: `[checkbox] {i+1}. {step.text with timer triggers}`
  - When `step.uses.length > 0`, render a thin second line below the text in monospace font: `{amount}{unit} {name}` separated by ` · ` (per-step compact display, mirrors current StepsList).
  - The "current" step gets a left Ochre border (2px) and slightly heavier text weight.
  - Checked steps get strikethrough + faded.
  - Auto-scroll the new "current" into view when a checkbox flips, using `scrollIntoView({ behavior: 'smooth', block: 'nearest' })`. Only scroll when the new current is offscreen.

### 4.5 Bottom timer dock (sticky)
Hidden when no timers running. Visible as a dark Obsidian bar across the bottom when there are.

Per timer row:
- Display in monospace, large: `42:13` (`< 1h`) or `1:23:45` (`>= 1h`).
- Below: `step N · {label}` in tiny faded text. (`step 0` for manual timers.)
- Pause/play toggle button.
- × remove button.

Right-edge of dock: a `+ Manual` button. Tap → small popover with three numeric inputs (`h`/`m`/`s`) + label text + `Start`. Adds a Timer with `stepIndex = -1`.

### 4.6 Quick-note FAB
- Floating action button bottom-right (above the dock when present, otherwise floats at bottom): `📝` icon (or thin-line SVG note icon).
- Tap → small modal with `Note for next batch` textarea + Save / Cancel.
- Saved notes accumulate in `quickNotes: string[]` (component-local; not persisted to the batch until End Cook).

## 5. Cook session state

Component-local `$state` on the cook page (not persisted before End Cook):

```ts
let started = $state(false);
let startedAt = $state<number | null>(null);
let checkedSteps = $state(new Set<number>());
let quickNotes = $state<string[]>([]);
let timers = $state<Timer[]>([]);
let endCookOpen = $state(false);
let wasFullChecked = $state(false);
```

Where:
```ts
type Timer = {
  id: string;            // crypto.randomUUID() or similar
  stepIndex: number;     // -1 for manual
  label: string;
  durationMs: number;
  startedAt: number;     // wall-clock epoch ms
  pausedAt: number | null;
  pausedAccumMs: number;
};
```

A single `setInterval(() => tickCounter++, 250)` increments a reactive `tickCounter`. Components compute remaining time per timer via `$derived` over wall-clock arithmetic — `tickCounter` is just the trigger, the actual math is `Date.now() - startedAt - pausedAccumMs - currentPauseSpan`. This keeps timers accurate even when the tab is backgrounded and the interval throttles.

The interval is owned by `CookView` and cleared in `onDestroy`. Same for the wake lock.

**Auto-prompt to End Cook:** a `$derived` over `(checkedSteps.size === recipe.steps.length && started && !wasFullChecked)`. When it transitions true, set `endCookOpen = true; wasFullChecked = true`. The flag prevents re-trigger if the user unchecks then rechecks. Manual `End Cook` button always opens it.

## 6. Inline timer parsing

Pure helper in `src/lib/ui/cook/layout/timer-parse.ts`:

```ts
export interface TimerMatch {
  start: number;           // index into source text
  end: number;             // exclusive
  durationMs: number;
  label: string;           // up to 4 surrounding words preceding the duration
}

export function parseTimers(text: string): TimerMatch[];
```

**Patterns** (case-insensitive, all require word boundaries on either side):
- `\d+\s*(seconds?|secs?|s)\b` — e.g. `30 s`, `30 seconds`, `5secs`
- `\d+\s*(minutes?|mins?|m)\b` — e.g. `45 min`, `30m`
- `\d+\s*(hours?|hrs?|h)\b` — e.g. `1 hour`, `5 hrs`, `2h`
- Compound: `\d+\s*(hours?|hrs?|h)\s+\d+\s*(minutes?|mins?|m)\b` — e.g. `1 hour 30 min`

The function scans left-to-right; compound matches are tried first so `1 hour 30 min` doesn't yield two separate matches. Overlapping matches are de-duplicated by keeping the leftmost-longest.

**False-positive guard:** if a match is preceded by a `°` character (with optional whitespace and digits between), skip it. e.g. in `475°F for 25 minutes`, the `25 minutes` parses fine but `475°F` doesn't get misinterpreted as a "475 minute" timer (it wouldn't anyway since `F` isn't a unit, but the guard catches edge cases like `5°S 30 min`).

**Label extraction:** for each match, take the up-to-4 words immediately preceding the duration (stopping at sentence-ending punctuation `. ! ? :`). Result like `rest`, `bulk ferment`, `bake covered`. If the duration is at the start of a sentence with no preceding words, label = `timer`.

**Pure-function unit tests** in `tests/ui/timer-parse.test.ts` cover all three units, compound, label extraction, °-guard, and zero-match input.

## 7. Step rendering with timer triggers

`CookStepRow.svelte` consumes `parseTimers(step.text)` and renders the step text as a sequence of plain spans + clickable timer-trigger buttons.

Pattern: split the source text into ranges using the matches. Each non-match range is `<span>`. Each match range is `<button class="dashed-underline ochre-text" onclick={() => startTimer(match)}>{...text...}</button>`.

Active timers (timer instance currently running for this match) get a different style: solid underline, Ochre background tint. Match identity is by `(stepIndex, start, end)`.

`data-testid="timer-trigger"` and `data-step={i}` and `data-start={match.start}` for E2E selector targeting.

## 8. Wake Lock

On `onMount`:

```ts
let wakeLock: WakeLockSentinel | null = null;
async function requestWakeLock() {
  try {
    wakeLock = await navigator.wakeLock.request('screen');
  } catch {} // unsupported or rejected
}
requestWakeLock();
```

Re-acquire on `visibilitychange` if the tab regains focus and `wakeLock` was released. Release in `onDestroy`.

Falls through silently in unsupported browsers (older Safari pre-16.4). Tests don't assert on it.

## 9. Quick-note FAB

Component: `CookQuickNoteFab.svelte`.

- Renders a fixed bottom-right button at z-50 (above dock).
- Click opens a modal (reuse the dialog pattern: `role="dialog" aria-modal="true" aria-labelledby="quick-note-title"`, backdrop click + Escape to close).
- Modal has: heading `Note for next batch`, textarea, Save / Cancel buttons.
- On Save: appends the trimmed text to `quickNotes` and closes. Empty notes ignored.
- A small badge on the FAB shows the count when `quickNotes.length > 0` (e.g. `3` in a circle).

## 10. End Cook flow

`EndCookDialog.svelte`. Opened via either the manual `End Cook` button or the all-checked auto-prompt.

**Dialog content:**

- Heading: `End Cook · {batch.label}` (first cook) or `End Re-cook · {batch.label}` (re-cook).

- **Cook session summary** (read-only stats panel):
  - `Elapsed: {formatted}` (e.g. `1h 12m`)
  - `Steps: {checked}/{total}`
  - `Timers: {count}` (number of timers started in this session, even if not finished)

- **Outcome notes textarea:**
  - First cook: label `Outcome notes`. Placeholder: `Crumb, crust, taste, what to change next time…`
  - Re-cook: label `Notes for this cook`. Placeholder same.

- **Rating** (1–5 stars) — first cook only. Hidden on re-cook.

- **Quick-notes recap** — only shown if `quickNotes.length > 0`:
  - Heading: `Improvement ideas captured during cook ({n})`
  - Bulleted list of notes
  - Checkbox: `[ ] Save these as a new draft batch` (default unchecked)
  - When checked, expand: input field `New batch label` with default `improvements from {batch.label}`

- **Buttons:** `Cancel` (closes dialog, session continues) · `Save Cook` (Juniper filled, primary).

**On submit:**

1. **First cook:**
   - PATCH `/api/recipes/{id}/batches/{batchId}` with:
     ```json
     {
       "status": "cooked",
       "cookedAt": "2026-05-15T18:30:00Z",
       "outcomeNotes": "...",
       "rating": 4,
       "cookDurationMs": 4320000
     }
     ```

2. **Re-cook:**
   - PATCH with only:
     ```json
     {
       "outcomeNotes": "{existing}\n\n— 2026-05-15:\n{new notes}"
     }
     ```
   - The append happens client-side from the read `batch.outcomeNotes` plus the new text.

3. **If "Save quick-notes as new draft batch" is checked** (either mode):
   - POST `/api/recipes/{id}/batches`:
     ```json
     {
       "label": "{user-typed label}",
       "description": "{bullet list of quick-notes}",
       "parentIds": ["{batchId}"],
       "status": "draft",
       "variables": { /* cloned from current batch */ },
       "ingredients": [ /* cloned */ ],
       "steps": [ /* cloned */ ]
     }
     ```
   - Defensive step-uses strip is unnecessary here (clone is identical, no ingredient set divergence).
   - **Note:** `Batch` doesn't currently have a `description` field — the description goes into `outcomeNotes` of the new draft instead, prefixed with `Captured during cook:\n`. (We could add a Batch description field later; YAGNI for now.)

4. After successful PATCH (and optional POST), navigate:
   - To `/recipes/{id}?batch={newDraftBatchId}` if a draft was created.
   - To `/recipes/{id}?batch={batchId}` otherwise.

**Server impact:** none. The existing PATCH handler already enforces frozen-fields on cooked batches (re-cook only sends `outcomeNotes` which is allowed). First-cook patches all fields, also allowed since the batch is `draft` at the time of patch.

**One change required to existing API client:** `api.createBatch` already supports the shape we need. ✓

## 11. New field on Batch

Add `cookDurationMs?: number` to `src/lib/server/domain/types.ts`'s `Batch` interface.

- Optional. Stored only when a first-cook is completed via cook view.
- Existing batches without the field: undefined. No migration. The read-time migration in `batches.ts` doesn't touch this field; default stays undefined.
- Display surfaces (BatchDetail, NotecardCard sparkline area, etc.) don't show the duration in MVP. Future: a small "Took 1h 12m" line under the cooked-date label on `BatchDetail`. Out of scope for the cook-view plan.

## 13. Testing

- **Unit:** `parseTimers` — comprehensive (s/m/h, compound, label extraction, °-guard, zero-match, mid-sentence vs sentence-start).
- **Unit:** the End Cook payload-building logic — extract a pure function `buildEndCookPatch(mode, sessionState)` and unit-test it (first-cook payload, re-cook append, fork POST shape).
- **Unit:** auto-prompt timing logic — extract `shouldPromptEndCook(checkedSteps, totalSteps, started, wasFullChecked)` if it makes sense; or rely on the E2E test.
- **E2E (`tests/e2e/cook.e2e.ts`):**
  1. Create a recipe + draft batch with steps containing `rest 5 min` style text.
  2. Open Cook view from BatchDetail.
  3. Verify mode tag = `Cooking`, Start Cooking banner present.
  4. Click `Start Cooking`. Banner unmounts; elapsed chip appears.
  5. Click a timer trigger. Bottom dock appears with a running timer.
  6. Check off all steps. Auto-prompt EndCookDialog opens.
  7. Fill outcome notes + rating. Submit.
  8. Lands on recipe detail; batch is now `cooked`; `cookDurationMs` is populated.
  9. Open Cook on the now-cooked batch. Mode tag = `Re-cook`. End Cook with notes. Verify the original `cookedAt` is preserved and `outcomeNotes` was appended-to.

## 14. Out of scope

- TTS / read-aloud for hands-free
- Voice input
- Per-step photos
- Batch scaling on the fly
- Mise-en-place pre-phase
- Multiple cook sessions stored as a list (`cookSessions: [{ at, durationMs, notes }]`)
- "Cook duration" displayed on BatchDetail (data is stored but not surfaced)
- Multi-recipe parallel cooking

## 15. Risks

- **Wake Lock unsupported:** older Safari. Wrapped in try/catch; falls through silently. No test assertion.
- **Notification permission:** asked once on first timer-done. If denied, fallback is in-page beep + visual pulse. Test simulates timer-done without relying on notifications.
- **Auto-scroll on step check:** could be jarring. Use `block: 'nearest'` so it only scrolls when needed.
- **Timer accuracy under tab throttling:** computed via wall-clock arithmetic, so backgrounded tabs still display correct remaining time on next tick. The 250ms tick may pause but won't drift.
- **Quick-note clone of variables/ingredients/steps:** cloning needs deep copy to avoid sharing references with the source batch. Use `structuredClone` or `JSON.parse(JSON.stringify(...))`.
- **Mobile Safari + sticky bottom dock:** iOS keyboard may cover the dock when typing in the quick-note modal. The modal is overlayed (z-50) and its own sticky context, so this should be fine; verify in E2E if the test framework allows.
